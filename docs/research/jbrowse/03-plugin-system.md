# 03 — The plugin system

> Source: JBrowse 2 v4.3.0, commit `83ac4507cf`, repo-relative paths.
> Everything in JBrowse 2 — adapters, tracks, displays, views, widgets, RPC
> methods, auth providers — is a **pluggable element** registered into a
> runtime registry (`PluginManager`). There is no plugin-side interface
> hierarchy beyond one abstract base class; a plugin is essentially a bag of
> side-effectful registration calls executed in a fixed phase order.

## 1. `Plugin` — the base class

`packages/core/src/Plugin.ts` (`abstract class Plugin`):

| member                              | what it is                                                                                                                                          |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name: string` (abstract)           | Registry key. Dedup key, UMD global suffix, config `plugins[]` name.                                                                                |
| `url?: string` / `version?: string` | Metadata; `url` set by the loader for runtime-loaded plugins.                                                                                       |
| `install(pm)`                       | Register pluggable element types + extension-point callbacks. Runs once, in `PluginManager.addPlugin`, **before** any element creation.             |
| `configure(pm)`                     | Second phase, after all `install`s and after `createPluggableElements()`; cross-plugin references (e.g. `pm.getDisplayType(...)`) are safe here.    |
| `uninstall(pm)`                     | Rarely implemented; removes the plugin from the manager (session plugin store).                                                                     |
| `configurationSchema?`              | Plugin-level config, namespaced under `configuration.<PluginName>` in the root config.                                                              |
| `configurationSchemaUnnamespaced?`  | Spread into the root config without the plugin name.                                                                                                |
| `rootConfigurationSchema?(pm)`      | Additional root-level config slots contributed by the plugin.                                                                                       |
| `exports` (set by plugin, not base) | Anything the plugin publishes to `globalThis` for other plugins/scripts (e.g. `WigglePlugin.exports = { utils }` in `plugins/wiggle/src/index.ts`). |

Lifecycle (`packages/core/src/PluginManager.ts`):

1. **Constructor** — instantiates `CorePlugin` (`packages/core/src/CorePlugin.ts`, registers core RPC methods, `CytobandAdapter`, format guessers, `BaseFeatureWidget`), then each initial plugin. `addPlugin` calls `plugin.install(pm)` **immediately** and pushes it; duplicate `name` is warn-and-skip (first wins — this prevents a bundled plugin plus a config entry from double-registering menu items, which are plain pushes with no guard).
2. **`createPluggableElements()`** — runs the deferred creation callbacks through a `PhasedScheduler` with a fixed group order: `adapter → text search adapter → display → track → connection → view → widget → rpc method → internet account → add track workflow`. Order matters because `addTrackType` retroactively attaches already-registered `DisplayType`s whose `trackType` matches, and `addViewType` does the same for `DisplayType.viewType`/`extendedName`.
3. **`configure()`** — runs every plugin's `configure(pm)`; sets `configured = true`; after this no new plugins may be added.

`Core-extendPluggableElement` fires once per element inside `createPluggableElements()`; registering on it after that point **throws** (it would silently never run). Same constraint: `addElementType` throws if called after `createPluggableElements()`.

## 2. Pluggable element types — full inventory

All element classes extend `PluggableElementBase` (`packages/core/src/pluggableElementTypes/PluggableElementBase.ts`): `name`, `maybeDisplayName`, and **`aliases?: string[]`** — older `type` strings remapped to this element when a session/config names them; the element owns its own renames (plus per-element `preProcessSnapshot` for property migrations; slot-value migrations use `addDisplayConfigMigration`).

Groups (the `PluggableElementTypeGroup` union in `PluginManager.ts`): `adapter`, `display`, `track`, `connection`, `view`, `widget`, `rpc method`, `internet account`, `text search adapter`, `add track workflow`. There is **no** `ViewContainerType` or `Theme` element type — themes are config/MUI, not registry entries.

Registry storage: one `TypeRecord` per group — a plain `{ [name]: ElementClass }` map with sorted `registeredNames()` and a `get()` whose error message lists what _is_ registered (so a build missing a plugin shows which group went missing). Lookups are all by string name: `pm.getAdapterType('BamAdapter')`, `pm.getRpcMethodType('CoreGetFeatures')`, etc. Misregistration is first-wins with a console warning.

| ------------------------- | -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

How the MST model unions get built: `pm.pluggableMstType(group, fieldName)` produces `types.union(...)` over every registered element's model (e.g. all track `stateModel`s), and `pm.pluggableConfigSchemaType(group)` unions all `configSchema`s — with a `snapshotProcessor` on the **track** union that runs `expandLooseTrackConfig` before MST validates. This union is embedded in the session/config schema, which is why a config's `tracks[].type` and `adapter.type` strings are the persistence keys.

## 3. Extension points

`PluginManager` keeps `extensionPoints: Map<string, Callback[]>` — a named chain of callbacks folded over a value. Three registration styles, enforced by TypeScript guard types (`AccumulatingPointName`, `NotificationPointName`, `FoldPointName` in `PluginManager.ts`):

1. **Fold (`addToExtensionPoint(name, cb)`)** — each callback receives the previous callback's return; last result wins. A callback returning `undefined` does **not** clobber — `nextAccumulator` warns and keeps the accumulator. Typed by declaration-merging into `interface ExtensionPointRegistry` (e.g. `'Core-extendSession': {args: IAnyModelType, result: IAnyModelType}`); `ViewTypeRegistry`/`DisplayTypeRegistry` similarly make `extendViewType(pm, 'LinearGenomeView', …)` a compile-checked name.
2. **Accumulating (`contributeToExtensionPoint`)** — declared with array `args`; the callback returns only _its own entries_ and the manager concatenates. Exists because hand-folding `[myEntry]` silently dropped other plugins' entries (the documented ABI hazard in `agent-docs/reference/PLUGIN_ABI_STABILITY.md`: a prebuilt v4 bundle still compiles against the loose overload and clobbers the array).
3. **Notification (`listenToExtensionPoint`)** — payload in `props`, return unread; async handlers are joined via `Promise.all` instead of the last promise replacing earlier ones. `extensionPointCallbackCount(name)` lets a caller distinguish "all handlers declined" from "nobody listening" (used by `waitForAssembly` on `Core-handleUnrecognizedAssembly`).

Evaluation variants: `evaluateExtensionPoint` (sync fold, **swallows callback errors** per-plugin so one failure doesn't sink the chain), `evaluateAsyncExtensionPoint` (same, awaiting each), `evaluateAsyncExtensionPointStrict` (does **not** swallow — for side-effect points like view launch), and `evaluateComponentExtensionPoint` (singular component slot: warns once when >1 plugin genuinely claims the slot; a wrapper built by `wrapComponent` carries a `wrappedComponent` Symbol so composition isn't counted as a clobber).

Component-point shapes: `ComponentSlot<P>` (one component, wrap-or-replace), `ComponentList<P>` (panel arrays), `ElementList<P>` (pre-rendered ReactNodes with keys fixed at registration).

Reachability of plugin-facing points is pinned by `packages/core/src/extensionPointReachability.test.ts` + `extensionPointShapes.test.ts`.

## 4. Plugin loading (`PluginLoader.ts`, `pluginDefinitions.ts`, `checkPlugins.ts`)

`PluginDefinition` union (`packages/core/src/pluginDefinitions.ts`): `umdLoc`/`umdUrl`/legacy `url` (UMD), `esmLoc`/`esmUrl` (ESM), `cjsUrl` (CJS, Electron/desktop only), and **`storePlugin`** (a plugin-store ref, resolved by `resolveStorePluginRefs` against `https://jbrowse.org/plugin-store/v2/plugins.json` into a version-pinned, integrity-hashed definition before it reaches the loader). All may carry an optional `name` and `integrity` (SRI hash). Helpers: `samePlugin` (dedupe by store-ref, name, or url), `dedupePlugins` (first source wins), `dropVendoredPlugins` (a product that bundles `MafViewer`/`GWAS` — plus desktop's `Blat` — drops a config's external copy; core's registration wins).

`PluginLoader` (`packages/core/src/PluginLoader.ts`):

- **UMD**: script tag injection (`loadScript`), optional SRI `integrity` (SRI and cache-buster `?_cb=` are mutually exclusive), then reads `globalThis['JBrowsePlugin' + name]` and takes `.default`. This is the classic third-party plugin path.
- **ESM**: `fetchESM` callback (dynamic `import()` in jbrowse-web), cache-busted url. CJS: only in Node/Electron via a `fetchCJS` callback.
- `assertSingleKind` throws if a definition names >1 loader kind — the guard that keeps "the url we vetted" equal to "the url we run".
- **Re-exports**: before any plugin bundle evaluates, `publishReExports` publishes `globalThis.JBrowseExports` (the `ReExports/index.ts` table, ~126 KB gzipped — lazily imported only when a runtime plugin actually loads) and sets the sync registry so `pluginManager.jbrequire('<package>')` works for CJS plugins. `PluginLoader.installGlobalReExports(target)` records the window/worker; `setReExportRegistry` feeds `pm.lib`/`pm.jbrequire`/`pm.load`.
- `loadSettled` loads all definitions with `Promise.allSettled` and returns `{records, failures}` — one bad plugin URL no longer kills session load (previously the only field in a config that could). The RPC worker keeps strict `load`.
- **Products**: `packages/product-core/src/loadPlugins.ts` (`loadRuntimePlugins`) is the shared body for embedded products; jbrowse-web/desktop wrap it. `lazyPluginExports` as such does not exist in this tree (appears in older docs); the lazy mechanism is the `ReExports/lazify.tsx` `lazyMap` + deferred `import('./ReExports/index.ts')`. Bundled plugins (web's `corePlugins`, desktop's, plus `Blat`) are simply constructed into the `PluginManager` constructor; config `plugins[]` for a name already bundled is skipped.
- **Version checks**: plugin-store manifest v2 has per-version JBrowse compatibility ranges + integrity hashes; resolution matches against the running `jbrowseVersion` (required argument, so a product can't silently resolve against the wrong host).
- **Trust gate** (`checkPlugins.ts`): `TRUSTED_PLUGIN_URL_PREFIXES = ['https://jbrowse.org/plugins/']`; store refs without a fallback URL are trusted by construction; anything else is checked against the store's URL set (`checkPluginsAgainstStore`) or the user is prompted (products own the prompt; desktop's `assertPluginsTrusted`). Loading a plugin runs its JS with full product privileges — in desktop, Node.

## 5. How tracks get wired

- A **track config** (JSON) carries `type` (a TrackType name) and `adapter: {type: <AdapterType name>, ...}`. MST resolves `type` through the union of all registered track `configSchema`s (`pluggableConfigSchemaType('track')`), and `adapter.type` through the adapter config union.
- The **track state model** (`createBaseTrackModel`, extended per TrackType) reads its config's `type`, then picks a display: candidate displays are `trackType.displayTypes` (populated at registration by `addTrackType`'s retroactive loop and by `addDisplayType` ordering) intersected with the view's `displayTypes` (`viewType.displayTypes`); see `packages/core/src/util/tracks.ts` (`getViewAndTrackType`, display-compatibility checks at lines ~800–990). A track config may also carry an explicit `displays: [{type: ..., ...slots}]` list whose entries win; a session display instance is a composed MST node of the DisplayType's `stateModel`.
- `DisplayType.viewType` is checked against the containing view; `extendedName` on a ViewType lets a subclass reuse another view's displays.
- Adapter selection at runtime: `pm.getAdapterType(config.adapter.type).getAdapterClass()` → instantiated inside the RPC worker (`dataAdapterCache`); capability strings drive menu availability (e.g. does the adapter support `getFeaturesInRegion`, export, etc.).
- Sequence for a plugin contributing a track (e.g. `plugins/alignments/src/index.ts`): adapter factories (`CramAdapterF`, `BamAdapterF`, `SamAdapterF`, `HtsgetBamAdapterF`) → track (`AlignmentsTrackF`) → display (`LinearAlignmentsDisplayF`) → widget (`AlignmentsFeatureWidgetF`) → RPC methods (`RenderAlignmentDataRPC`), all via the per-directory `index.ts` factory `f(pm)` pattern. `plugins/wiggle/src/index.ts` shows the same plus plugin `exports` and shared RPC methods added directly (`pm.addRpcMethod(() => new MultiWiggleGetScoreMatrix(pm))`).

## 6. Widgets and internet accounts (brief)

- **Widgets** are session records: `session.addWidget(typeName)` instantiates the WidgetType's `stateModel`; the drawer widget renders the active widget's `ReactComponent`. `Core-replaceWidget` can substitute the renderer for any widget (scoped by `model.type`, and for feature widgets by `trackId`/`trackType`); `Core-extraFeaturePanel` appends cards. `BaseFeatureWidget` (CorePlugin) is the generic feature-detail widget; displays can override `featureWidgetType` (a hook) to use their own.
- **Internet accounts** (`InternetAccountType`) are configured per config `internetAccounts[]`; the root model's `findAppropriateInternetAccount(resolvedUri)` matches on host/URL prefix. Before any RPC whose args contain a `UriLocation`, `RpcMethodType.augmentLocationObjects` walks the args and calls `account.getPreAuthorizationInformation(loc)` to attach `internetAccountPreAuthorization` (token etc.) so the **worker** can fetch authenticated data without main-thread help. Desktop file handles become `BlobLocation`s with a deterministic `fh-blob-<handleId>` id in the same walk.

## 7. Plugin ABI stability (`agent-docs/reference/PLUGIN_ABI_STABILITY.md`, `packages/core/src/ReExports/`)

- **Surfaces that ossify**: `ReExports/modules.ts` (the `@jbrowse/core/*` subpaths + framework packages external plugins resolve globally), the published `exports` map of `@jbrowse/core` (generated from in-repo import sites — the last importer leaving un-publishes a subpath), the session model, and the **accumulating extension points** (worst: an old-style callback returns its own array and silently drops every other plugin's entries — nothing throws).
- **Checks**: `ReExports/abi.test.ts` pins `modules.ts` against `abiBaseline.json`; `pluginFacingSessionApi.test.ts` pins (and _calls_) the 15 session members published bundles actually use; `workspaceLayering.test.ts` pins package direction (no plugin → product dependency). Baselines for plugin-exports/session-exports were tried and dropped as not worth it at current plugin count. `publishedPluginBreaks.json` records breaks already shipped.
- **Removed from the re-export surface (v4.3→v5)**: the entire renderer registry (`RendererType`, `BoxRendererType`, `ServerSideRendererType`, …), the layout classes, AbortSignal helpers → stop tokens, desktop file-handle cache, 48 names over 55 entries. 16 deep-import subpaths also left the published `exports` map. Lesson: **a plugin-facing argument may be added optional, never required** — the signature is as public as the name. Still unchecked: props of exported components (a removed prop on a prebuilt bundle is silently ignored by React).
- `pm.jbrequire(name)` / `pm.load(fn)` give runtime plugins the host's shared singletons (React, MobX, MUI, core utils) instead of bundling duplicates — the mechanism depends on the re-export list, which is why it is ABI.

## Mab notes

- The whole plugin model reduces to **named string registries + phased registration callbacks** — trivially portable to Rust as `HashMap<&str, Box<dyn Element>>` per group plus an install/configure two-phase boot. You lose dynamic loading, which is arguably a feature: a Rust browser can just compile adapters in and use the same _registry_ idea for dispatch keys.
- **Persistence keys are the strings.** Session/config JSON stores `type: "AlignmentsTrack"`, `adapter.type: "BamAdapter"`; aliases + first-wins registration + a union type for validation are the compatibility machinery. In Rust, keep a stable `&'static str` per element and a versioned schema for each element's config — the config _is_ the interchange format.
- Extension points: adopt the three-style distinction (fold / accumulate / notify) and especially **accumulate-by-contribution, never hand-folded arrays** — the documented JBrowse ABI bug. Rust trait objects + `Vec` append makes the accumulating form the natural default.
- Adapter guessing (`Core-guessAdapterForLocation` first-match-wins chain + `adapterCapabilities` + `normalizeSnapshot` shorthand expansion) is a good, small subsystem to copy almost verbatim: a priority list of `fn(&Location) -> Option<AdapterConfig>`.
- RPC method registry keyed by name with both args and return checked against one registry entry is exactly the pattern to reproduce with a Rust enum or a typed trait with associated `Args`/`Return`.
- The manager's error discipline is worth imitating: `get()` errors list registered names; per-callback failures are isolated on fold points but propagate on side-effect points; batch loads settle rather than fail.
- Trust/integrity: if Mab ever loads native code, mirror the "vet exactly the url that runs" rule (`assertSingleKind`) and settle-based batch loading.
- Avoid the renderer-registry era entirely: JBrowse is deleting it (displays own rendering via lifecycle mixins). A new design should make the display the rendering unit from day one — no separate renderer layer to remove later.
- Ambiguity noted: `lazyPluginExports` (mentioned in older JBrowse docs) does not exist in this tree; laziness is `ReExports/lazify.tsx` + deferred dynamic import of the re-export table.
